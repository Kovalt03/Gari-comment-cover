# 아키텍처

댓글 필터링 확장의 구조와 그렇게 정한 이유를 적는다.

확정되지 않은 내용은 문장 안에 표시한다.

- `(미결정)` 선택지는 알지만 아직 고르지 않은 것. 10절에 목록이 있다
- `(검증 예정)` 사실이라고 가정하고 설계했지만 아직 실제로 확인하지 않은 것
- `(고려사항)` 결정에 영향을 주지만 지금 판단할 근거가 부족한 것

표에 적힌 지연과 처리 비율은 전부 목표치이며 측정값이 아니다.

## 1. 문제

유튜브 댓글 중 사용자가 보고 싶지 않은 것을 화면에 나타나기 전에 접는다.
무엇을 접을지는 고정된 규칙이 아니라 사용자가 접어온 이력에서 학습한다.
판정은 브라우저 안에서 끝나고 댓글 텍스트는 외부로 나가지 않는다.

설계는 다음 제약을 따른다. 충돌하는 경우 위쪽이 우선한다.

1. 걸러야 할 댓글이 한 프레임도 렌더링되지 않을 것
2. 재현율보다 정밀도. 잘못 접은 댓글은 사용자가 알려줄 경로가 없다
3. 댓글 텍스트가 기기를 벗어나지 않을 것
4. 댓글 한 건당 비용이 상수에 가까울 것. 영상 하나에 수백 건이고 스크롤에 따라 계속 늘어난다
5. 사이트 마크업이 바뀌었을 때 고칠 파일이 한 곳일 것

1번이 2번보다 위에 있는 것이 이 설계의 출발점이다.
정확한 판정보다 노출되지 않는 것이 먼저이기 때문에, 뒤에 나오는 숨김 구조와 실패 처리가 모두 여기서 나온다.

## 2. 실행 컨텍스트 배치

Manifest V3에서 확장 코드가 실행될 수 있는 위치는 세 곳이고 성질이 다르다.
임베딩 모델을 어디에 둘지가 첫 번째 구조 결정이다.

| | content script | service worker | offscreen document |
|---|---|---|---|
| DOM 접근 | 페이지 DOM | 없음 | 자체 문서 |
| 수명 | 탭과 동일 | 유휴 시 종료 | 사용 중 유지 |
| 인스턴스 수 | 탭마다 | 하나 | 확장당 하나 |
| WebGPU | 페이지 CSP 영향 | 제약 있음 | 사용 가능 (검증 예정) |
| IndexedDB | 페이지 origin | 확장 origin | 확장 origin |

service worker는 유휴 상태에서 종료되므로 모델을 올리면 재시작마다 수십 MB를 다시 로드한다.
content script는 탭마다 생성되므로 같은 사이트를 여러 탭에 띄우면 모델이 그만큼 중복된다.
또 content script가 접근하는 IndexedDB는 확장이 아니라 페이지 origin의 것이라 판정 캐시를 둘 수 없다.

남는 것은 offscreen document다. 확장당 하나만 존재하고, 사용 중에는 종료되지 않으며, DOM과 WebGPU에 접근한다.

다만 offscreen document는 생성 시 사유(reason)를 명시해야 하고 목록이 고정되어 있다.
추론 용도에 해당하는 항목이 있는지, ONNX Runtime Web이 이 컨텍스트에서 WebGPU 백엔드로 동작하는지는
아직 확인하지 않았다. (검증 예정)

```
+---------------------+     +---------------------+     +---------------------+
|  content script     |     |  service worker     |     |  offscreen doc      |
|  one per tab        |     |  one per extension  |     |  one per extension  |
|                     |<--->|                     |<--->|                     |
|  DOM handling       |     |  message routing    |     |  ONNX Runtime       |
|  L0 memory cache    |     |  IndexedDB          |     |  embed + classify   |
|  L1 rules           |     |  user profile       |     |  L3 calls           |
+---------------------+     +---------------------+     +---------------------+
```

캐시 조회와 규칙 판정은 content script에 남겨두었다.
규칙으로 처리되는 비율을 30~50%로 잡고 있고, 이만큼을 메시지 왕복 없이 같은 컨텍스트에서 끝낼 수 있다.
이 비율은 라벨링한 평가셋으로 확인하기 전까지는 가정이다. (검증 예정)
프로세스 간 통신 비용은 실제로 모델이 필요한 댓글에만 붙는다.

대신 content script의 캐시는 메모리에 있어 페이지 전환 시 사라진다.
영상을 열 때마다 해당 영상 몫을 다시 받아와야 한다.
워밍업 단위는 아직 정하지 않았다. (미결정 · 10절)

## 3. 숨김이 적용되는 시점

제약 1번은 판정 시점이 아니라 주입 시점의 문제다.
JavaScript로 요소를 숨기면 이미 늦다.

`manifest.json`의 `content_scripts[].css`로 선언한 스타일시트는 문서 파싱 이전에 적용된다.
같은 항목의 JavaScript는 `run_at`을 `document_start`로 두어도 그보다 뒤에 실행된다.
이 순서가 실제 유튜브에서도 성립하는지는 더미 필터로 확인한다. (검증 예정)
따라서 숨김은 선언형 CSS가 담당하고, 스크립트는 통과한 댓글을 여는 일만 한다.

```json
{
  "content_scripts": [{
    "matches": ["https://www.youtube.com/*"],
    "css": ["hide.css"],
    "js": ["content.js"],
    "run_at": "document_start"
  }]
}
```

처리 순서는 다음과 같다.

```
CSS가 댓글 영역을 숨김 (파싱 이전)
        |
MutationObserver가 삽입된 댓글 노드를 감지
        |
L0 -> L1 -> (필요 시) L2 -> (드물게) L3
        |
통과한 노드에 클래스를 부여해 표시
```

기본 상태가 숨김이므로 파이프라인이 지연되거나 실패해도 걸러야 할 댓글이 노출되지 않는다.
반대로 파이프라인이 완전히 멈추면 아무것도 보이지 않는다. 7절에서 다룬다.

## 4. 어댑터와 코어

코어는 DOM을 다루지 않고 텍스트와 식별자만 받는다.
브라우저 없이 테스트하기 위한 것이고, 동시에 제약 5번을 만족시키는 방법이기도 하다.
마크업에 의존하는 코드는 전부 어댑터 안에 있다.

```typescript
interface SiteAdapter {
  readonly siteId: string;

  // manifest에 선언할 CSS 경로. 스크립트로 주입하지 않는다
  readonly hideStylesheet: string;

  // 관찰 대상 루트. 아직 존재하지 않으면 null을 반환해 재시도하게 한다
  getObserverRoot(): Element | null;

  // 삽입된 노드에서 댓글을 추출한다. 대댓글을 포함한다
  extractComments(node: Node): CommentEntry[];

  reveal(entry: CommentEntry): void;
  collapse(entry: CommentEntry, reason: FilterReason): void;

  // SPA 전환 통지. 유튜브는 영상 전환 시 문서를 다시 로드하지 않는다
  onNavigate(cb: (pageId: string) => void): void;
}

interface CommentEntry {
  id: string;        // 사이트 내에서 안정적인 식별자
  text: string;
  el: Element;       // 어댑터 내부에서만 사용한다. 코어로 전달하지 않는다
}
```

`onNavigate`가 인터페이스에 포함된 이유는 유튜브가 영상을 바꿔도 문서를 다시 로드하지 않기 때문이다.
전환을 감지하지 못하면 이전 영상의 판정 상태와 관찰자가 그대로 남는다.

인터페이스는 정의하되 구현은 유튜브 하나만 둔다.
두 번째 사이트를 붙이는 시점에 맞지 않는 부분이 드러나면 그때 수정한다.
사이트를 여러 개 가정하고 미리 추상화하면 첫 번째 사이트조차 제대로 동작하지 않는 경우가 많다.

## 5. 필터 파이프라인

| 단계 | 실행 위치 | 방식 | 목표 지연 | 목표 처리 비율 |
|---|---|---|---|---|
| L0 | content script | 메모리 캐시 | 1ms 미만 | 재방문 시 대부분 |
| L1 | content script | 정규식, 링크 패턴, 반복 문자, 금지어 | 1ms 미만 | 30~50% |
| L2 | offscreen | 문장 임베딩 + 경량 분류기, 배치 | 10~50ms | 45~65% |
| L3 | offscreen | LLM 재판정 | 수백 ms | 5% 미만 |

각 단계는 세 가지 중 하나를 반환한다.

```typescript
type Verdict =
  | { kind: 'pass' }
  | { kind: 'hide'; reason: FilterReason }
  | { kind: 'unsure' };
```

`unsure`를 별도로 둔 것은 제약 2번 때문이다.
확신이 없는 댓글을 접는 쪽으로 기울이면 정밀도가 떨어지고, 그 손실은 사용자에게 보이지 않는다.
판단이 서지 않으면 다음 단계로 넘기고, 마지막 단계에서도 서지 않으면 통과시킨다.

L2는 단건이 아니라 배치로 호출한다.
MutationObserver가 감지한 댓글을 수십 ms 단위 윈도로 모아 한 번에 추론한다.
윈도 길이와 배치 크기는 추론 속도를 측정한 뒤 정한다. (미결정)
댓글마다 추론을 호출하면 목표 지연을 맞출 수 없다.

이 구조에서 측정해야 할 값은 각 단계의 처리 비율과 지연 분포다.
특히 정확도를 유지하면서 L3 호출 비율을 얼마나 낮출 수 있는지가 이 설계의 성패를 판단하는 기준이 된다.

## 6. 저장소

모두 확장 origin의 IndexedDB에 둔다.

| 저장소 | 내용 | 수명 |
|---|---|---|
| `verdicts` | 댓글 해시 → 판정 결과와 판정 단계 | LRU, 크기 상한 |
| `profile` | 사이트별 임베딩 중심점과 누적 횟수 | 영구 |
| `metrics` | 단계별 처리 건수, 지연 분포 | 링 버퍼 |

캐시 상한과 링 버퍼 크기는 정하지 않았다. (미결정)

댓글 원문은 저장하지 않고 해시를 키로 쓴다. 작성자 정보는 추출 단계에서 버린다.

`metrics`는 기능이 아니라 계측 장치지만 처음부터 포함한다.
단계별 비율이 이 프로젝트의 결과물이고, 나중에 붙이면 이전 상태와 비교할 수 없다.

## 7. 개인화

사용자가 댓글을 접으면 해당 임베딩이 사이트별 프로필에 누적되고 이후 판정에 반영된다.
라벨이 없는 초기에는 사전 정의 카테고리로 시작해, 이력이 쌓일수록 개인 프로필의 가중치를 높인다.
사이트마다 댓글의 문체와 길이가 다르므로 프로필은 사이트 단위로 분리한다.

여기에는 아직 해결하지 못한 문제가 있다.
접는 행동은 명확한 부정 신호지만, 접지 않은 댓글이 긍정 신호라고 볼 근거는 없다.
읽지 않고 지나쳤을 수도 있고 스크롤 밖에 있었을 수도 있다.
양성 라벨만 관측되는 상황의 학습(PU learning)에 해당한다. (미결정 · 10절)

접힌 댓글만 학습하면 프로필이 초기 몇 건에 과도하게 끌려갈 수 있다는 점도 함께 봐야 한다. (고려사항)

## 8. 실패 처리

숨김이 기본 상태이므로 파이프라인이 멈추면 댓글이 전부 사라진다.
이는 제약 1번을 택한 결과이고 구조적으로 피할 수 없다. 대신 사용자에게 선택권을 준다.

타임아웃이 지나도 판정이 오지 않으면 숨김을 유지한 채 배너를 표시한다.
타임아웃 값은 인위적 지연을 넣어 체감으로 정한다. (미결정 · 10절)
자동으로 전부 표시하는 동작은 설정에서 선택할 수 있게 하되 기본값으로 두지 않는다.
기본값을 fail-open으로 두면 확장이 조용히 무력화된 상태를 사용자가 알 수 없다.

| 상황 | 동작 |
|---|---|
| 셀렉터가 아무 노드도 찾지 못함 | 마크업 변경으로 간주, 경고 표시 후 필터 중단 |
| 모델 로드 실패 | L1까지만으로 동작, 배지로 상태 표시 |
| WebGPU 미지원 | WASM 백엔드로 폴백 |
| offscreen 무응답 | 타임아웃 후 배너 |

## 9. L3의 위치

L3는 선택 사항이다. 사용할 수 없는 환경에서도 제품이 성립해야 한다.

Chrome Built-in AI(Prompt API)는 2026년 9월 기준 다음 조건을 요구한다.
여유 저장공간 22GB, VRAM 4GB 초과 GPU 또는 16GB RAM과 4코어 이상, 모델 다운로드를 위한 무제한 네트워크.
지원 OS는 Windows 10/11, macOS 13 이상, Linux, Chromebook Plus이며 Android와 iOS는 제외된다.
확장에서는 Chrome 138부터 안정 단계로 분류되지만 플래그 활성화가 필요하다는 보고가 있고,
폭넓은 stable 제공 시점은 Chrome 145~150으로 알려져 있다.
공식 문서와 실사용 보고가 엇갈리므로 실제 기기에서 확인한 결과를 기준으로 삼는다. (검증 예정)

조건을 충족하는 사용자 비율이 높지 않다고 보고 다음과 같이 처리한다.

```typescript
const state = await LanguageModel.availability();
// 'available' | 'downloadable' | 'downloading' | 'unavailable'
```

- `unavailable`이면 L2에서 `unsure`로 남은 댓글을 통과시킨다. 접지 않는다
- 모델 다운로드를 사용자 동의 없이 시작하지 않는다. 수 GB 규모다
- 외부 API는 기본 경로에 포함하지 않는다. 사용하는 경우 별도 동의를 받는다

이 API의 상태는 자주 바뀌므로 가용성 판정은 기동 시 한 번 조회한 결과를 사용하고,
조회 시점을 기록해둔다.

## 10. 미결정 항목

결정되면 `docs/decisions/`에 ADR로 기록한다.

| # | 항목 | 선택지 | 결정에 필요한 것 |
|---|---|---|---|
| 1 | 빌드 도구 | Vite / esbuild | 진입점 구성과 모델 파일 번들링 요구사항 |
| 2 | L0 캐시 워밍업 단위 | 페이지 단위 선반입 / 요청 시 적재 | 캐시 적중률과 워밍업 지연 측정값 |
| 3 | 임베딩 모델 | 미정 | 후보별 크기, 다국어 품질, 추론 속도 실측값 |
| 4 | 분류 방식 | 프로토타입 유사도 / 로지스틱 회귀 | 확보 가능한 라벨 수와 두 방식의 비교 결과 |
| 5 | 미관측 신호 처리 | 미정 | 7절의 비대칭을 어떻게 다룰지에 대한 결론 |
| 6 | fail-safe 타임아웃 값 | 미정 | 지연을 주입했을 때의 체감 한계 |
| 7 | 모델 배포 방식 | 확장에 번들 / 원격 다운로드 | MV3의 CSP 제약과 확장 크기 제한 확인 결과 |

1번은 코드를 쓰기 전에 필요하고 나머지는 해당 값을 측정한 뒤에 정한다.
근거가 나오기 전에 정하면 ADR에 기록할 내용이 남지 않는다.
