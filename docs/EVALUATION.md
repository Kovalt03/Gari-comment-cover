# 평가 방법

이 문서는 무엇을 어떻게 측정할지를 정한다.
측정 절차를 구현보다 먼저 고정해두기 위한 것이고, 이후 리포트의 숫자는 전부 여기 정의를 따른다.

절차를 나중에 정하면 결과가 나온 뒤에 유리한 기준을 고르게 된다.
그런 숫자는 개선을 증명하지 못한다.

## 1. 평가 대상

두 가지를 따로 본다.

- 정확도: 접어야 할 댓글을 접었는가, 접지 말아야 할 댓글을 남겼는가
- 성능: 사용자가 기다리는 시간과 자원 사용량

둘은 맞바꿀 수 있는 관계라 같은 표에 놓고 본다.
정확도가 올라도 지연이 목표를 넘으면 채택하지 않는다.

## 2. 라벨

수집한 댓글에 다음 중 하나를 부여한다.

| 라벨 | 정의 |
|---|---|
| `spam` | 광고, 링크 유도, 자동 생성으로 보이는 반복 게시 |
| `toxic` | 인신공격, 혐오 표현, 과도한 공격성 |
| `unwanted` | 위 둘은 아니지만 개인적으로 보고 싶지 않은 것. 스포일러, 특정 주제 등 |
| `neutral` | 무해함 |
| `ambiguous` | 판단이 서지 않음 |

`unwanted`는 라벨을 붙인 사람의 기준에 의존한다. 이 프로젝트가 다루려는 대상이기도 하다.
라벨링 시 어떤 기준으로 `unwanted`를 골랐는지 함께 기록한다.
기준을 적어두지 않으면 나중에 모델이 무엇을 학습했는지 설명할 수 없다.

`ambiguous`는 버리지 않는다. 이 집합의 크기와 내용이 모델의 한계 지점을 그대로 보여준다.
평가 시에는 별도로 집계하고 정밀도 계산에서는 제외한다.

### 우회 표기 여부

라벨과 별개로, 필터를 피하려고 표기를 비튼 댓글인지 표시한다.
자모 풀어쓰기, 이모지나 기호 끼워 넣기, 모양이 비슷한 문자 치환 등이 해당한다.

이 표시가 있어야 우회 표기에 대한 성능을 따로 잴 수 있다.
전체 정밀도가 높아도 우회 표기에서만 크게 떨어진다면 규칙 기반 계층의 한계가 거기 있다는 뜻이다.

## 3. 데이터셋

### 구성

성격이 다른 영상에서 수집한다. 예능, 시사, 게임, 음악, 교육 등을 섞는다.
영상 장르에 따라 댓글의 길이와 문체가 크게 달라지므로, 한 장르에 치우치면 규칙과 모델이 그 장르에만 맞는다.

수집은 확장의 수집 모드로 한다. 실제 판정과 같은 추출 코드를 쓰기 위해서다.
별도 경로(API, 스크래퍼)로 모으면 화면에 보이는 텍스트와 형태가 달라지고, 평가 결과가 실사용과 어긋난다.

- 대댓글과 이모지만 있는 댓글도 포함한다
- 정렬은 인기순을 기본으로 하고 최신순을 일부 섞는다.
  유튜브는 최신순에만 스팸 가능성이 있는 댓글을 포함하므로, 인기순만으로는 스팸 표본이 거의 모이지 않는다
- 영상 정보(제목, 설명, 카테고리, 키워드)를 함께 저장한다. 영상 맥락을 반영하는 실험에 쓴다

수집 항목의 전체 목록과 보관 방침은 `PRIVACY.md` 8절을 따른다.

### 중복

같은 텍스트는 한 번만 저장하고 등장 횟수와 등장한 영상 목록을 함께 기록한다.
비교 기준은 기본 정규화(NFC, 제로폭 문자 제거, 공백 정리)를 거친 텍스트다.

중복을 버리지 않는 이유는 반복 게시 자체가 스팸 신호이기 때문이다.
여러 행으로 두지 않는 이유는 같은 문장이 학습셋과 테스트셋에 동시에 들어가는 것을 막기 위해서다.

작성자 정보를 수집하지 않으므로, 한 계정의 반복 게시와 여러 사람이 같은 말을 쓴 경우는 구분할 수 없다.

### 분리 규칙

학습, 검증, 테스트 분리는 댓글 단위가 아니라 영상 단위로 한다.

같은 영상의 댓글은 주제와 어휘를 공유한다.
댓글 단위로 섞어서 나누면 테스트셋에 학습셋과 거의 같은 문장이 들어가고 성능이 실제보다 높게 나온다.
영상 단위로 나누면 처음 보는 주제에 대한 성능을 측정하게 된다.

같은 텍스트가 여러 영상에 등장하면 그 텍스트는 한쪽 집합에만 넣는다.
영상 단위로 나눠도 텍스트가 겹치면 누수가 생긴다.

## 4. 정확도 지표

접는 것을 양성으로 둔다.

| | 실제로 접어야 함 | 실제로 남겨야 함 |
|---|---|---|
| 접음 | TP | FP |
| 남김 | FN | TN |

- 정밀도 = TP / (TP + FP). 접은 것 중 실제로 접어야 했던 비율
- 재현율 = TP / (TP + FN). 접어야 할 것 중 실제로 접은 비율

두 오류의 비용이 다르다.

FN은 걸러야 할 댓글이 노출된 경우다. 사용자가 그 댓글을 접으면 그 자체가 학습 신호가 되어 다음에 반영된다.
FP는 남겨야 할 댓글을 접은 경우다. 접힌 상태로 시작하므로 사용자는 무엇이 사라졌는지 모른다.
확인하지 않으면 알 수 없고, 알 수 없으니 피드백도 오지 않는다.

따라서 정밀도를 우선 지표로 쓴다.
F1은 참고용으로만 기록하고 채택 기준으로 쓰지 않는다. 두 오류를 같은 비중으로 취급하기 때문이다.

### 클래스 불균형

`neutral`이 전체의 대부분을 차지할 것으로 예상된다. (검증 예정)
이 상황에서 정확도(accuracy)는 의미가 없다. 전부 남기기만 해도 높게 나온다.

그래서 정확도는 기록하지 않는다.
대신 클래스별 정밀도와 재현율, 그리고 혼동 행렬 전체를 리포트에 싣는다.

## 5. 계층별 측정

전체 정확도만으로는 어느 계층이 기여했는지 알 수 없다.
각 계층에 대해 다음을 따로 집계한다.

| 항목 | 의미 |
|---|---|
| 처리 비율 | 그 계층에서 `pass` 또는 `hide`로 끝난 댓글의 비율 |
| 통과 비율 | `unsure`로 다음 계층에 넘긴 비율 |
| 계층별 정밀도 | 그 계층이 `hide`로 판정한 것 중 실제로 접어야 했던 비율 |
| 지연 분포 | 중앙값, p95 |

가장 중요한 값은 L3 호출 비율이다.
정확도를 유지하면서 이 값을 얼마나 낮출 수 있는지가 이 설계의 성패를 판단하는 기준이다.

L2를 도입한 뒤에는 L1만 사용했을 때의 결과와 나란히 놓고 본다.
L2가 L1 결과를 유의미하게 넘지 못하면 모델을 유지할 이유가 없다.
이 경우 가설이 틀렸다는 사실과 그 원인을 기록하는 것이 결과가 된다.

## 6. 성능 지표

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| 첫 댓글 표시까지 지연 | 300ms 미만 | Performance API |
| 댓글 100건 처리 시간 | 500ms 미만 | 배치 단위 계측 |
| 모델 초기 로드 | 3s 미만, 캐시 후 500ms 미만 | |
| 메모리 증가량 | 200MB 미만 | Chrome 작업 관리자 |
| L3 호출 비율 | 5% 미만 | 카운터 |

목표치이며 측정값이 아니다.

측정 규칙은 다음과 같다.

- 첫 실행은 버린다. 모델 로드와 JIT 워밍업이 섞인다
- 같은 조건에서 여러 번 측정하고 중앙값을 쓴다. 평균은 이상치에 흔들린다
- 분포가 넓은 항목은 p95를 함께 적는다
- 측정 환경(기기, 크롬 버전, WebGPU 사용 여부)을 리포트에 명시한다. 환경이 다르면 비교할 수 없다

## 7. 개인화 평가

여기에는 정답 집합이 존재하지 않는다.
`unwanted`의 기준이 사람마다 다르므로, 고정된 평가셋으로는 개인화의 효과를 측정할 수 없다.

현재 계획은 사용 로그를 기준으로 하는 것이다.
개인화를 적용하기 전과 후에 각각 일정 기간 사용하면서, 사용자가 직접 접은 횟수와 펼친 횟수를 센다.
직접 접는 횟수가 줄면 재현율이 개선된 것이고, 펼치는 횟수가 늘면 정밀도가 나빠진 것이다.

이 방식에는 한계가 있다. 사용자가 한 명이고, 기간에 따라 보는 영상이 달라진다.
통계적으로 유의한 비교는 어렵다고 보고, 경향을 보는 용도로만 쓴다. (고려사항)

## 8. 리포트

측정 결과는 `docs/` 아래에 남긴다. 각 리포트는 다음을 포함한다.

- 측정 환경과 데이터셋 버전
- 이전 결과와의 비교
- 목표 대비 달성 여부
- 목표에 못 미친 항목의 원인 분석

개선되지 않은 결과도 기록한다.
실패한 실험의 기록이 없으면 무엇을 시도했는지 알 수 없고, 같은 시도를 반복하게 된다.
